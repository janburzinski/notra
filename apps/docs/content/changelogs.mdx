Notra generates changelogs from your GitHub pull requests, commits and releases, and optionally from Linear issues. Each changelog starts as a draft post that you review, refine it with the content agent and publish it when ready.

Changelogs live in the Studio content pipeline, so in the dashboard you switch the sidebar to **Studio** and open **Content**.

## How it works

<Steps>
  <Step title="Connect a source">
    Install the Notra GitHub app on the repositories you want to cover, and optionally connect Linear so issues show up as source material. See [GitHub](/integrations/github) and [Linear](/integrations/linear).
  </Step>

  <Step title="Create on demand or automate">
    Click **New post** on the Content page to generate a changelog right now, or set up a schedule or an event trigger so Notra generates one for you. See [Scheduled Automation](/automation/scheduled) and [Event-Based Automation](/automation/event-based).
  </Step>

  <Step title="Notra reads your activity">
    The changelog agent pulls the activity inside the lookback window, filters out work that is only relevant internally, and groups the rest by impact and category.
  </Step>

  <Step title="Review and publish">
    The changelog appears as a draft in a collection. Open it, edit it directly or ask the content agent for changes, then click **Publish**.
  </Step>
</Steps>

## Create a changelog manually

<Steps>
  <Step title="Open the create dialog">
    Go to **Content** and click **New post**.
  </Step>

  <Step title="Formats">
    Pick **Changelog entry**. You can select several formats at once, for example a changelog plus a LinkedIn post, and Notra generates all of them from the same activity. Choose a lookback window and toggle which data points to include: **Pull Requests**, **Commits** and **Releases**.
  </Step>

  <Step title="Activity">
    Pick the repositories and Linear integrations to draw from, and Notra previews the releases, pull requests, commits and issues in the window. Deselect anything you do not want mentioned, and search by title, author or label to find items.
  </Step>

  <Step title="Identity">
    Choose which brand identity writes the post. Notra then generates the posts into a new collection and opens each one in the editor when it is ready.
  </Step>
</Steps>

## Changelog structure

Every generated changelog follows the same shape, and the agent leaves out any section that would be empty.

### Title and excerpt

The title names the two or three biggest changes, like "Sites for every workspace, one Analytics page and Autopilot workflows". The excerpt is one sentence that a site uses as the card text and page summary.

### Action required

Breaking changes and anything you have to do come first, with what changed, who is affected and what to do.

### One section per big change

The one to three biggest changes each get their own section. A section starts with a sentence or two on what changed, followed by bullets for the details.

### Also new and Fixes

Every other change is one bullet under **Also new**, starting with the product area in bold. **Fixes** lists what works now, written from the reader's side.

<Note>
  The agent reads the description of every merged pull request, not just its title, and leaves out internal work such as refactors, tests, CI and dependency updates. It also leaves out changes that aren't live yet, such as work behind a feature flag that is still off.
</Note>

### Links

The agent links a feature to its documentation or product page when your brand identity's crawled sitemap has one, and never makes up a URL. Pull request links only appear for a public repository and a developer audience, because links into a private repository return 404 for readers.

## Lookback windows

The lookback window controls how far back Notra looks for activity when it generates a changelog on demand or on a schedule.

| Window         | Description             | Best for                |
| -------------- | ----------------------- | ----------------------- |
| `current_day`  | Today's changes only    | Real-time daily updates |
| `yesterday`    | Previous day's activity | Morning recaps          |
| `last_7_days`  | Past week (default)     | Weekly team updates     |
| `last_14_days` | Past two weeks          | Bi-weekly releases      |
| `last_30_days` | Past month              | Monthly summaries       |

<Info>
  Event triggers do not use a lookback window, so for a GitHub release event, Notra compares the new release with the previous one and uses that range.
</Info>

## Tone

The agent writes in the tone profile of the brand identity you pick: **Conversational**, **Professional**, **Casual** or **Formal**. You set it under **Studio > Brand Identity**, together with your target audience and custom instructions. See [Brand Voice](/concepts/brand-voice).

## Automation settings

<Visibility for="agents">

Schedules and event triggers that produce changelogs accept these options, and the same fields are available in the dashboard and in the public API (`POST /v1/schedules` and `POST /v1/event-triggers`).

**Scheduled generation**

```json
{
  "name": "Weekly changelog",
  "sourceType": "cron",
  "sourceConfig": {
    "cron": { "frequency": "weekly", "hour": 9, "minute": 0, "dayOfWeek": 1 }
  },
  "targets": { "repositoryIds": ["repo_123"] },
  "outputType": "changelog",
  "outputConfig": { "brandVoiceId": "bv_123" },
  "lookbackWindow": "last_7_days",
  "enabled": true,
  "autoPublish": false
}
```

`frequency` is `daily`, `weekly` (requires `dayOfWeek`, 0 to 6) or `monthly` (requires `dayOfMonth`, 1 to 31). `hour` is 0 to 23 and `minute` is 0 to 59.

**Event-based generation**

```json
{
  "sourceType": "github_webhook",
  "sourceConfig": { "eventTypes": ["release"], "includePreReleases": true },
  "targets": { "repositoryIds": ["repo_123"] },
  "outputType": "changelog",
  "outputConfig": { "brandVoiceId": "bv_123" },
  "enabled": true,
  "autoPublish": false
}
```

`eventTypes` accepts `release` and `push`.

</Visibility>

### Auto-publish

Changelogs and blog posts support **Auto-publish**, and when it is on, Notra saves generated posts with the `published` status immediately instead of as drafts. Notra always saves social posts and images as drafts.

## Publishing

Clicking **Publish** in the editor (or enabling auto-publish) sets the post status to `published` but does not push the post anywhere by itself. Instead, your publishing destinations pick up published posts:

* **Framer**: the Notra plugin imports your posts into a Framer site. See [Framer](/integrations/framer).
* **Manual**: copy the Markdown from the editor.

<Visibility for="agents">

* **Your own site or CMS**: fetch posts from the API with `GET /v1/posts?status=published` and render them on your site. See [API Getting Started](/api/getting-started).

</Visibility>

**Move to draft** takes a published post back to `draft`.

## Edit with the content agent

Every post has a content agent in the right-hand panel. Select text in the editor to give the agent context, then ask for changes such as:

* "Add the pricing change to Also new"
* "Simplify the Analytics section for a non-technical audience"
* "Move the caching change into Also new"

The agent edits the post in place, and you can review the diff before it saves.

## Best practices

### Write clear PR titles and descriptions

Notra uses your PR titles and descriptions as source material, so descriptive PRs produce better changelogs.

**Good PR title**\
`Add email verification flow with expiration handling`

**Poor PR title**\
`Fix bug`

Start each description with what changed for your users. Notra reads the first few hundred characters of every PR and the full description only for the biggest changes. PRs titled with a [Conventional Commits](https://www.conventionalcommits.org) type that never reaches users (`build`, `chore`, `ci`, `docs`, `refactor`, `revert`, `style`, `test`) are skipped unless the type has the `!` breaking-change marker. PRs from dependency and CI bots like Dependabot or Renovate are skipped too. PRs from coding agents are read like any other.

### Match the lookback window to your release cadence

* If you ship daily, use `yesterday` or `current_day`
* For weekly releases, use `last_7_days`
* For monthly updates, use `last_30_days`

### Review before publishing

Changelogs stay drafts until you publish them, so use the review to:

* Verify technical accuracy
* Add context that GitHub activity does not capture
* Adjust which changes get their own section

## Example changelog

```markdown
# One Analytics page and Sites for every workspace

## One Analytics page

Website traffic and social analytics used to live on separate pages. They're
now one **Analytics** page with three tabs: Website, MCP server and Social.

- **MCP server analytics:** see which agents call your MCP server and which
  tools they use.
- **Clearer setup:** AI traffic tracking is now a short list of numbered steps.

## Notra Sites is open to every workspace

Any workspace can now host a blog or changelog from a GitHub repository.

- **[IndexNow](https://www.usenotra.com/docs/sites/integrations/search/indexnow):**
  new and changed posts are sent to Bing after a production deploy.

## Also new

- **Members** can leave an organization from **Settings → Members**.

## Fixes

- Post to X no longer publishes the same post twice.
```

## Common issues

### Changelog is too short or missing expected changes

The lookback window may not cover the relevant timeframe, the activity may have been deselected in the Activity step or the PRs may lack detail. To fix it:

1. Check the lookback window against when the work was merged
2. Make sure the PRs, commits or releases were selected in the Activity step
3. Add descriptive titles and descriptions to your PRs

### Nothing was generated

Every plan includes a monthly quota of long-form posts, and changelogs and blog posts count against it. When the quota is used up, Notra falls back to AI credits, and if none are available, Notra blocks the generation.

To fix it, check **Settings > Billing & Usage > Usage**, and top up credits under **Settings > Credits** or upgrade the plan. See [Billing & Plans](/organization/billing).

### Changes from private repositories not appearing

The GitHub app is not installed on the repository, or the repository is disabled in the integration. To fix it:

1. Navigate to **Integrations > GitHub**
2. Add the repository, or enable it if it is already listed
3. Re-run the generation
